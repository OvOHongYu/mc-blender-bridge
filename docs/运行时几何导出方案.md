# 运行时几何导出方案（R17）

> 目标：让 Blender 侧能拿到**模组方块真实渲染出来的几何**，而不是靠逐块手工反推。
> 本文说明问题定位、三条可行路径的取舍、以及已完成的验证原型。

## 1. 问题定位

静态烘焙（`tools/bake_assets.py`）只读资源：blockstate → 模型 JSON（含 parent /
`neoforge:obj` / `neoforge:composite`）。据此对 Create 6.0.10 的覆盖统计
（探针 `dist/_r16_coverage.py`）：

| 类别 | 数量 | 说明 |
| -- | -- | -- |
| 静态完整 | 582 | blockstate 引用链能把几何解析齐全 |
| **需运行时部件** | **54** | 机器方块：几何由渲染器在运行时生成 |
| 空模型（纯 BE） | 7 | 连静态模型都没有 |

那 61 个"机器方块"里，部件模型（partial model）**是躺在 jar 里的**，问题有两层：

1. **引用不可见**：它们只被 Java 字节码引用（`AllPartialModels`、各 `*Renderer` /
   `*Visual` 类），blockstate JSON 从不提到，静态扫描看不到 → 表现为"孤儿模型"；
2. **姿态是运行时决定**：即便找到模型，用哪个部件、什么朝向、显示几份，取决于
   邻居连接、动力网络、转动相位、内容物等**运行时状态**，资源里没有答案。

第 1 层可以靠读字节码人工补齐（R12 的做法，已补 ~20 个方块）；第 2 层靠人工
反推必然反复出错——这正是这个项目连续三轮"补了又缺"的根本原因。

## 2. 三条采集路径

| 路径 | 做法 | 覆盖 | 代价 / 风险 |
| -- | -- | -- | -- |
| A. 手工部件表 | 读字节码定位模型 + 手写朝向（现方案） | 姿态固定者 | 每块人工验证；姿态运行时决定者做不对 |
| B. **世界内运行时捕获** | 让游戏按规范布局摆好方块，劫持该帧顶点提交，抄下目标方块周围的几何 | 代码生成模型 + BE 渲染器 + Flywheel（在其取得批次缓冲的前提下） | 需要一个能跑客户端的原型与调试；Flywheel 是主要未知 |
| C. 帧缓冲体素化 | 截图 + 深度转网格 | 一切可见物 | 质量差（遮挡/分辨率）、需重建 UV，不推荐 |

**选 B。** 决定性理由：它与"几何从哪来"解耦——不管是原版 BE、第三方 Flywheel、
还是自己实现 `BakedModel` 的模组，只要最终经顶点管线提交，就能抓；而且抓到的是
**渲染器自己算出来的结果**，不需要理解它的逻辑。

## 3. 目标架构

```
   /api/capture?x&y&z&r&ms        （HTTP，脚本驱动）
              │
              ▼
   GeometryCapture.arm(...)       （共享静态状态；单人游戏客户端/集成服务端同 JVM）
              │
              ▼
   MultiBufferSourceMixin         （客户端：BufferSource#getBuffer 出口套记录层）
              │  tee：顶点照常转发 → 画面不受影响
              ▼
   QuadRecorder                   （累积顶点 → 四边形 → 命中目标盒才留存）
              │
              ▼
   /api/capture/result            （JSON：逐 RenderType 统计 + 命中四边形）
              │
              ▼
   Blender 侧烘焙：把捕获结果落成模型（后续）
```

要点：

- 注入点 `MultiBufferSource.BufferSource#getBuffer` 是**所有**世界几何汇入 GPU 前的
  共同咽喉，且是纯原版类——**不需要依赖 Create/Flywheel 的编译期 API**，
  不随模组升级失效；
- 捕获是 **tee（旁路）**：顶点照常写给真身，画面与性能只有一小段窗口受影响；
- 目标方块用**空间盒**筛选（默认半径 2.5 格），顺带回答"提交坐标是世界坐标还是
  相机相对坐标"（后者需减去相机位置才能切到方块局部空间）；
- 触发走 HTTP 而非客户端命令/按键：复用本项目已有 API，且**便于脚本批量驱动**
  （遍历方块 × 规范布局）。

## 4. 已完成：验证原型

代码（`mcmod-neoforge/src/main/java/com/zcube/mcbridge/`）：

| 文件 | 职责 |
| -- | -- |
| `capture/GeometryCapture.java` | 状态 / 统计 / 报表；**不引用任何客户端类**，服务端侧安全 |
| `capture/QuadRecorder.java` | 客户端：tee 型 `VertexConsumer`，累积四边形 |
| `mixin/MultiBufferSourceMixin.java` | 客户端 mixin：在 `getBuffer` 出口挂记录层 |
| `http/ApiServer.java` | 新增 `/api/capture`、`/api/capture/result` |
| `src/main/resources/mcbridge.mixins.json` | 记录层 mixin 放进 `client` 数组（专用服务端不加载） |

用法（游戏内已进入世界，且**把目标机器摆在视野内**）：

```
GET http://127.0.0.1:8788/api/capture?x=<方块x>&y=<方块y>&z=<方块z>&r=2.5&ms=1500
GET http://127.0.0.1:8788/api/capture/result
```

报表同时打印到游戏日志/控制台，并落盘到 `<运行目录>/mcbridge-capture/capture.{txt,json}`。

**判读标准**（原型要回答的三个问题）：

1. `renderType` 列里是否有**实体/方块实体层**的条目且「命中盒」> 0
   → Flywheel 的几何确实经过 `BufferSource`，可捕获；
2. 命中是否集中在少数几个 `renderType`（对应 Create 用的层）→ 后续按层过滤即可；
3. 「x 范围」列：数值接近世界坐标 → 直接减方块原点；在 0 附近摆动
   → 提交的是相机相对坐标，需加相机位置。

## 5. 限制与风险（必须写清楚）

- **姿态依赖运行状态者，捕获也只给"某一时刻的姿态"**：链传动轮的外壳按邻居
  连接取舍、传送带形状取决于两轴之间的路径、绳索长度、机械臂关节角、
  装置运动中的活塞——这些没有唯一答案。做法是约定**规范布局**（孤立摆放 /
  三条直线 / 成对），导出"该约定下的姿态"。这已比人工反推准得多，但用户会看到
  "与游戏里那一瞬间不完全一致"，属原理限制。
- **需要真实客户端**：要 GPU、要进入世界；服务端单跑无效。
- **单人游戏前提**：arm 走 HTTP（集成服务端），几何记录在客户端——两者必须同 JVM。
  独立服务端 + 独立客户端时该链路不通（后续可改为客户端侧轮询指令）。
- **Flywheel 版本风险**：本方案只依赖 `BufferSource`，比直接调 Flywheel API 稳，
  但若某版本绕过 `BufferSource` 自建缓冲，则抓不到——正是原型要先验证的点。
- 原型未做：纹理名还原（UV 落在图集坐标，需反查 sprite）、四边形的材质/混合层
  归类、批量遍历、生成 MCBA 条目。

## 7. 全链路实现（已落地）

| 环节 | 实现 |
| -- | -- |
| 捕获 | 客户端 mixin + tee 记录器（§4） |
| **纹理还原** | 客户端在捕获窗口开启时建一次**图集 sprite 表**（`GET /api/capture/sprites`）：枚举 `textures/block/**.png` → 逐个查 `getTextureAtlas(...)` 给的查找函数 → `[u0,v0,u1,v1, 源贴图路径]`。导出时把图集 UV 折算成「源贴图 + sprite 内 0..1」，v 翻转对齐 Blender 约定 |
| **方块归属** | 世界坐标 = 相机 + 相对；按 `floor` 归属到方块并转成**方块局部 1/16 单位**；`GET /api/block?x&y&z` 取该方块的**状态名**（如 `create:gearshift[axis=y,powered=false]`） |
| **批量导出** | `tools/capture_export.py`：arm 一次大半径捕获 → 归属 → 纹理还原 → 按**状态**聚合 → 写 `dist/runtime_models.json` |
| **接入烘焙** | `bake_assets.py --runtime-models <json>`（默认自动加载 `dist/runtime_models.json`）：按 `(方块, 属性集)` 精确挂到对应**状态**；该类状态**整体取代**静态模型链 + 部件表（捕获时状态已应用过），未捕获的状态自动回退静态路径 |

用法：

```
# 1. 游戏内进入世界、把机器摆在视野里
python tools/capture_locate.py            # 可选：先看哪里有运行期几何
python tools/capture_export.py --center auto --radius 8
#   -> dist/runtime_models.json

# 2. 重烤资产包（会自动带上运行时几何）
python tools/bake_assets.py <客户端jar> <mods/*.jar> --mc-version 1.21.1 -o dist/assets.mcba
```

## 10. R17b：Flywheel 视觉层捕获（决定性补全）

### 10.1 原方案的天花板（实测）

R17（拦原版 `MultiBufferSource`）**只能覆盖走原版 RenderType 的 Create 几何**
（`BacktankRenderer`/`ShaftRenderer` 等经 `SuperByteBuffer` 提交的部分）。实测：

- 在 `create:crushing_wheel` 位置把捕获盒从 r=2 放大到 r=6，**三层全 0 命中**；
  Create 6 的机关本体是 **Flywheel 视觉**（`*Visual`），以 **GPU 实例化**渲染——
  顶点进的是 GPU 缓冲、按实例在着色器里变换，**根本不经过任何 `VertexConsumer`**；
- Flywheel 1.0 只注册了 `flywheel:instancing` / `flywheel:indirect` 两个后端，
  **没有非实例化回退**，无法"逼它走原版管线"；
- 证据：`entity_translucent_cull` 里的几何**塌缩进 0.19 单位小盒、半径放大也不扩散**，
  正是实例化批次局部空间的产物。

### 10.2 方案：挂 Flywheel 的 instancer / 视觉层（拿到真值）

Flywheel 的每个 `Visual` 绑定一个方块实体（携带 **BlockPos**），而几何来自
`InstancerProvider#instancer(InstanceType, Model, bias)` 的 **`Model`**。于是：

| 环节 | 实现 |
| -- | -- |
| **归属** | mixin `BlockEntityStorage#createRaw`：视觉构造前后置线程局部「当前方块(pos+状态名)」 |
| **几何** | mixin `InstancerProviderImpl#instancer`：出口记录 `(方块, Model, InstanceType)`；跳过 `SHADOW` |
| **取顶点** | `Model#meshes()` → `Mesh#write(MutableVertexList)`（自实现记录器）直接读出顶点；按 `QuadIndexSequence` 每 4 顶点成四边形 |
| **触发** | mixin `Minecraft#runTick` 帧末轮询：捕获窗口内做**一次**快照 |
| **坐标** | 模型顶点在**方块局部空间**；以最大绝对坐标启发式判定单位（0..1 直用 / 0..16 除以 16），换算成相机相对坐标喂进既有管线 |

代码：`capture/FlywheelCapture.java` + `mixin/{BlockEntityStorageMixin,
InstancerProviderImplMixin,MinecraftTickMixin}.java`。构建脚本把 Create 内嵌的
Flywheel jar 加进编译类路径。

### 10.3 烘焙端：静态底座 + 捕获几何**合并**

机器方块常是**静态模型（机架/外壳）+ 运行时运动部件（Flywheel）**两段
（如 `mechanical_press` 的静态模型有 4 个 element 的机架；`crushing_wheel` 静态为空）。
故 `bake_assets.py` 对该状态：**静态模型几何（仅当确有 elements）+ 捕获几何**，
不再"整体取代"，避免丢底座。

### 10.4 实机结果（基地 25 状态 / 13 种机器）

一次基地捕获 → 重烤，导出状态含：`belt`、`crushing_wheel[axis=x/y]`、
`encased_fan[3 向]`、`gearshift[3 轴]`、`mechanical_drill`、`mechanical_mixer`、
`mechanical_press`、`speedometer`、`stressometer`、`hand_crank`、`chain_conveyor`、
`copper_backtank` —— **正是此前"缺失"的那批**。`assets.mcba` 重烤后，
**近似几何兜底清单里机器全部消失**（只剩巧克力/水/屏障等本就无模型的方块）。
破碎轮等已渲染成可辨认的模型（带辐条 + 黄铜轴心）。

### 10.5 实例变换：对照着色器修正（已实现）

Create 的机关实例是**自定义实例类**（不是 Flywheel 内置的 OrientedInstance）：
`RotatingInstance`（动力学传动）、`ScrollInstance`（燃烧室滚动）、`TransformedInstance`。
读它们的公开字段（反射，避免硬依赖），并**对照顶点着色器**还原变换：

| 实例 | 着色器 | 变换 |
| -- | -- | -- |
| `RotatingInstance` | `create:flywheel/instance/rotating.vert` | `kineticRot·(R·(v−0.5)) + pos + 0.5` |
| `ScrollInstance` | `create:flywheel/instance/scrolling.vert` | `R·(v−0.5) + pos + 0.5` |
| `TransformedInstance` | `flywheel:.../transformed.vert` | `pose·v` |

**关键坑（已定位并修正）**：实例的 `x/y/z` 是 **「世界 − 渲染原点」**，而渲染原点
**不等于**方块位置（实测方块 (120,−60,−395) 的实例 xyz=(−13,−7,3)，渲染原点≈(133,−53,−398)）。
- `RotatingInstance`/`ScrollInstance` 的 `+pos` 项恰好与渲染原点抵消，故
  `local = R·(v−0.5) + 0.5`；
- `TransformedInstance` **没有**这个抵消，必须显式加回渲染原点：
  `local = pose·v + renderOrigin − blockPos`。早期用 `pose·v − pose 平移列` 是**错的**
  （实测手摇柄手柄偏 1 格）——这是前几轮"施加变换反而更差"的真正原因。

实现上：mixin 里读 `VisualizationManagerImpl.renderOrigin()` 得到渲染原点，按上述两式换算。
**法线也要随同一变换旋转**——否则烘焙端按法线算的面朝向 `dir` 会错，导致背面剔除
把旋转过的部件"藏掉一半"。

另有：Flywheel **复用 Instancer**（同一 `(type, model)` 共用一个），故实例归属必须用
**`createInstance` 时的线程局部当前方块**，不能按 Instancer 对象映射。

自转相位（`kineticRot` 随 `renderSeconds` 变化）是动画，烘焙取静止姿态，略去。

**跨方块几何的归属**：机器几何常**伸进相邻方块**（如 `hand_crank` 的摇柄伸出到邻格局部 x<0）。
早期导出端按"四边形质心所在方块"归属，会把伸出部分丢进空气方块而剔除。改为：Flywheel 侧
按层名 `flywheel@x,y,z` **携带源方块**，导出端直接归属该方块、不做质心重判——手摇柄 9 面→34 面、
机械钻 206→254 面，伸出部分恢复。


### 10.6 UV 归属：sprite 边界 bug（已修）

图集里 sprite 紧密相邻；四边形 UV 正好压在**共享边界**上时（顶点落进邻居矩形内一点点），
逐顶点判定会把四边形判给**左邻居**。实测：机械搅拌器的杆压在相邻的纯红 `create:block/indicator/6`
上 → 木杆显示成红色格子。

修复：导出端改用**四边形 UV 质心**判定 sprite（质心失败再退回逐顶点投票），并改**半开区间**。
验证：搅拌器几何解析为 `mechanical_press_pole`(52) + `waterwheel_metal`(12) + `mixer_head`(18)
+ `cogwheel`(72)，与 Create 的 `mechanical_mixer/pole.json`（textures = waterwheel_metal +
mechanical_press_pole）**完全一致**，红色消失。

### 10.7 捕获盒裁剪 & UV 越界（已修）

- **"平放粉碎轮只有一半"**：捕获盒原来按**四边形质心**裁剪，压在盒边界的方块被切掉一半
  （实测 3 个 `axis=y` 粉碎轮正好在 (116,−60..−58,−389)、距盒心 12 = 半径）。
  改为**按方块归属**——方块中心在范围内就收录其**全部**几何（含伸出邻格部分）。
  验证：`crushing_wheel[axis=y]` 420→**804 面** = 3 × 268（正好 3 个堆叠轮），渲染出完整轮盘。
- **局部 UV 越界**：模型 UV 比 sprite 矩形略大（~0.5%），采到邻居/内边距。修复：导出端把
  局部 UV **钳到 [0,1]**。验证：20840 个 UV 顶点越界 0。
- **工具**：导出端改为**轮询到超时**（原来只轮询一次，采集稍慢就误报 404）。

## 11. 兼容性：能否兼容机械动力的附属模组？

**理论上能**，因为本方案挂在**渲染管线**而非按方块名硬编码——附属模组只要复用
Create 的渲染路径就自动被覆盖：

| 几何来源 | 抓法 | 附属是否自动覆盖 |
| -- | -- | -- |
| blockstate JSON 静态模型 | 静态烘焙器（读资源包） | ✅ 所有模组通用 |
| **Flywheel 视觉**（Create/附属的机器） | `BlockEntityStorage#createRaw` + `InstancerProviderImpl#instancer` + 顶点 tee | ✅ 用 Flywheel 即抓 |
| 原版 `BlockEntityRenderer` | `MultiBufferSource#getBuffer` 顶点 tee | ✅ 通用 |

**明确的失败边界**：

1. **贴图不在 `blocks` 图集 / 自定义图集** —— UV→源贴图是拿 blocks 图集反查的，换图集会解析错（**最大风险**）；
2. **自定义实例类** —— 实例变换靠反射读 `rotation`/`x,y,z`/`pose` 字段，读不到 → 退化为模型自身姿态；
3. **非 Flywheel、非 BER 的自绘管线**（自建 deferred/GL）—— 抓不到；
4. **强依赖运行时状态的姿态**（绳索长度、机械臂关节、装置动画）—— 只给捕获瞬间的姿态；
5. **世界里未出现的方块** —— 不覆盖；
6. **Flywheel 版本不同** —— mixin 针对 Create 1.21.1 内置的 Flywheel 1.0.x，错版可能失配。
